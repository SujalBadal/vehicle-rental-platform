# Smart Car Rental — System Design

This document describes the implementation currently present in this repository. It was checked against the frontend routes and components, backend route registrations and controllers, Mongoose models, package manifests, and `server/.env.example`. Where the requested workflow differs from the code, the current behavior is described instead.

## 1. Project overview

Smart Car Rental is a single-business vehicle rental management application. The React client supports customers, staff, and administrators. The Express API handles authentication, role checks, bookings, fleet operations, payments, rental handovers, maintenance, notifications, invoices, and business settings. MongoDB stores application records; Cloudinary stores uploaded vehicle images and the business logo.

Current workflows:

- **Customer:** register or log in, browse vehicles and check availability, create and track bookings, view recorded payments and invoices, manage their profile.
- **Staff:** log in, work with bookings and fleet operations, record payments, handle pickups and returns, schedule maintenance, view notifications and profile. A Staff dashboard and a staff-only reports page are also registered.
- **Admin:** log in to the Admin dashboard, manage staff, vehicles, categories, bookings, payments, and business settings. Admin routes also exist for rentals, invoices, and maintenance. The Admin dashboard currently shows basic totals, recent bookings, and quick links.

Booking review is performed by Staff or Admin. Payment records are entered by Staff or Admin; the code does not process card or UPI transactions through a payment gateway. Customers can create accounts through public registration, which assigns the customer role.

## 2. System goals and implemented scope

Implemented capabilities include vehicle and category management, date-based booking availability, customer booking requests, staff/admin booking decisions, payment receipt recording, pickup and return records, maintenance records, invoice generation, business settings, notifications, and role-based access control.

Business settings represent one rental business. Reports API endpoints exist and a Staff-only report page is routed in the client. Features such as online payment processing, multi-tenant businesses, or a separate audit-log workflow are not evidenced by the current implementation and are not described as available features.

## 6. Role-based access control

Roles are `admin`, `staff`, and `customer`. The server uses JWT authentication middleware and role authorization middleware. Client `ProtectedRoute` checks the current user and permitted roles for page access; backend checks remain the authority for API access.

| Capability | Customer | Staff | Admin |
|---|---:|---:|---:|
| Public vehicle/category browsing and availability | Yes | Yes | Yes |
| Create booking | Yes | No | No |
| View own booking/payment/invoice data | Yes | — | — |
| View and manage bookings | Own records; eligible cancellation | Yes | Yes |
| Approve/reject booking | No | Yes | Yes |
| Create/update vehicles and upload images | No | Yes | Yes |
| Delete vehicles | No | No | Yes |
| Manage categories | No | No | Yes |
| Record payment | No | Yes | Yes |
| Pickup/return and maintenance operations | No | Yes | Yes |
| Manage staff accounts | No | No | Yes |
| Business settings | No | No | Yes |
| Notifications and own profile | Own | Own | Own |
| Reports API | No | Yes (revenue endpoint is Admin-only) | Yes |

Some shared client routes allow both Staff and Admin, while the reports page route is Staff-only. Exact endpoint permissions are summarized in Section 21.

## 7. Frontend architecture

`client/src/main.jsx` mounts the React app with `BrowserRouter` and `AuthProvider`. `App.jsx` registers public, authenticated, and role-restricted paths. `ProtectedRoute` handles authentication/loading and checks `allowedRoles`; `AuthenticatedLayout` and `Sidebar` provide shared authenticated navigation where used. Customers retain their customer-facing navigation treatment.

`AuthContext` stores the signed-in user, loading/error state, and notification data/unread state, and exposes authentication-related actions. The API client in `services/api.js` uses Axios and adds `Authorization: Bearer …` from browser `localStorage` when an access token exists. Forms use component state and `react-hook-form`; no Redux store was found.

Important routes include `/admin/dashboard`, `/admin/staff`, `/admin/vehicles`, `/admin/categories`, `/admin/bookings`, `/admin/payments`, and `/admin/business-settings`; Staff routes include `/staff/dashboard`, `/staff/bookings`, `/staff/vehicles`, `/staff/rentals`, `/staff/payments`, `/staff/maintenance`, and `/staff/reports`; customer routes include `/customer/dashboard`, `/customer/bookings`, `/customer/payments`, and `/customer/invoices`. Shared feature routes such as `/profile` and `/notifications` are protected. See Section 21 for a backend route inventory.

## 8. Backend architecture and request lifecycle

`server/src/app.js` configures Helmet, single-origin CORS, JSON parsing, authentication rate limits, mounts route modules under `/api/v1`, and returns a JSON 404 for unmatched API paths. Route modules connect URL/method combinations to controller functions and apply authentication/role middleware. Controllers validate request data, read or update Mongoose documents, call small services when needed, and return JSON responses. Mongoose schemas define persisted fields, indexes, and some validation.

```text
HTTP request → Express app/router → authentication → role/ownership checks
             → controller validation/workflow → service and/or Mongoose
             → MongoDB or Cloudinary → JSON/PDF response
```

There is no separate general-purpose validators module in the inspected tree. Validation is distributed between controllers, middleware, and Mongoose schemas. `config` contains database startup configuration; `utils` contains shared helpers. Services currently include Cloudinary upload and notification operations. An Express error handler normalizes upload and unexpected server errors.

## 9. Database design

The inspected Mongoose models are:

| Model | Purpose and key fields | Relationships |
|---|---|---|
| `User` | Account name, unique lowercase email, hidden bcrypt password, normalized mobile, role, active flag, optional driving-license number/expiry; timestamps | Referenced by bookings, payments, rentals, maintenance, notifications, invoices, and audit logs |
| `Category` | Unique name, description, active flag; timestamps | One category can be referenced by many vehicles |
| `Vehicle` | Category, make/model/year, unique uppercase registration, description, transmission, fuel type, seats, daily price, image URL/public-ID pairs, status, internal booking lock version; timestamps | References Category; referenced by Booking, Rental, Maintenance |
| `Booking` | Customer, vehicle, pickup/return dates and location, copied daily rate, total price, status, reviewer/time, rejection reason, internal payment lock version; timestamps | References User customer, Vehicle, optional reviewer User; referenced by Payment, Rental, Invoice |
| `Payment` | Booking, customer, amount, method, received/refunded status, optional transaction reference, recording user, receipt time; timestamps | References Booking and User records |
| `Rental` | Unique booking reference, vehicle/customer, active/completed status, pickup/return timestamps and odometers, condition notes, damage flags/notes; timestamps | References Booking, Vehicle, and User customer |
| `Maintenance` | Vehicle, service type/description, status, schedule/completion dates, cost, notes, creator/performer; timestamps | References Vehicle and User records |
| `BusinessSettings` | Singleton key, business name, contact/address fields, GSTIN, optional logo URL/public ID; timestamps | One settings record is used by the single-business application |
| `Invoice` | Unique invoice number and booking reference, optional payment, customer, amount, issue time, optional PDF URL; timestamps | References Booking, Payment, and User customer |
| `Notification` | Recipient, type, title/message, optional read time; timestamps | References recipient User |
| `AuditLog` | Actor, action, target type/id, summary, mixed details; timestamps | References actor User; target is represented by type and ID |

Enums and indexes are schema-defined. Booking dates are validated so return is later than pickup. `Vehicle.bookingLockVersion` and `Booking.paymentLockVersion` are internal concurrency fields. MongoDB references are Mongoose document references; they are not relational-database foreign keys.

```text
User (customer) 1 ── * Booking * ── 1 Vehicle * ── 1 Category
                       │   │             │
                       │   ├── * Payment  └── * Maintenance
                       │   ├── 0..1 Rental ─── Vehicle
                       │   └── 0..1 Invoice
                       └── User (reviewer)

User 1 ── * Notification
User 1 ── * Maintenance (creator / performer)
User 1 ── * AuditLog (actor)
BusinessSettings: one singleton document for this business
```

The schema enforces one Rental and one Invoice per Booking through unique booking indexes/references. AuditLog exists as a model, but a writer, route, or UI using it was not found.

## 10. Customer booking data flow

1. A customer registers or logs in and receives an access token.
2. The client browses vehicles and may request availability for selected dates.
3. The customer submits a booking with a vehicle, dates, and pickup location.
4. The API validates IDs, date format/order, that pickup is not in the past, and vehicle status/date conflicts.
5. A transaction creates a pending booking using a server-calculated duration, copied daily rate, and total price.
6. Staff or Admin can approve or reject a pending booking. The decision and reviewer/time are stored; rejection reason is retained when supplied.
7. Staff or Admin records the full outstanding payment amount against an eligible approved/completed booking.
8. Staff or Admin records pickup and return. A successful return completes the rental and, when still approved, the booking.

Booking statuses in the schema are `pending`, `approved`, `rejected`, `cancelled`, and `completed`. A booking can be cancelled by its customer or Staff/Admin only while pending/approved and before its pickup date.

## 11. Vehicle availability flow

Availability checks consider existing bookings with status `pending` or `approved`. A conflict exists when:

```text
existing.pickupDate < requested.returnDate
AND
existing.returnDate > requested.pickupDate
```

The strict comparisons allow one booking to end exactly when another begins. The vehicle must also be in an eligible available state. Booking creation repeats the availability check on the server inside a MongoDB transaction. It increments `Vehicle.bookingLockVersion` in that transaction so concurrent requests for the same vehicle conflict/retry rather than both relying on a stale availability read. Transactions require a MongoDB deployment that supports them, such as a replica set or Atlas cluster.

## 12. Payment data flow

Staff/Admin record a payment for an approved or completed booking. Supported methods are `cash`, `upi`, and `card`; the amount must equal the currently outstanding balance. The controller calculates that balance from payment records whose status is `received`, then creates a `received` Payment document within a transaction. A booking lock field serializes concurrent payment recording. The outstanding amount is derived from `Booking.totalPrice` minus received payments; Booking does not store a separate payment-status field.

This is payment receipt recording. No online payment gateway, card authorization, or card-number storage is implemented. A recorded receipt can later have status `refunded` in the Payment model; the inspected payment recording flow creates `received` records. Invoices use booking, customer, vehicle, received payments, and business settings.

## 13. Pickup and return flow

Staff/Admin perform rental operations. Pickup requires an approved booking, a pickup date that has arrived, a vehicle that is available, and full payment. Pickup captures an odometer reading and condition notes, creates one active Rental for the booking, and changes vehicle status to `rented`.

Return requires an active rental and a return odometer at least as high as the pickup reading. It stores return time, odometer, condition notes, and optional damage details. The rental becomes `completed`; the associated booking is changed from `approved` to `completed`; the vehicle becomes `available`, or `maintenance` when damage is reported. The inspected model/controller do not have a fuel-level field or a separate return fuel workflow.

## 14. Maintenance flow

Staff/Admin can create and update maintenance records, start scheduled work, complete it, or cancel it. Records include vehicle, service type, description, status (`scheduled`, `in_progress`, `completed`, or `cancelled`), scheduled/completed times, cost, notes, and creating/performing users. Scheduling maintenance places the vehicle in `maintenance`; completing or cancelling restores it to `available` only when the vehicle is still marked as in maintenance. Return damage can also place the vehicle in maintenance.

## 15. Cloudinary image flow

The frontend submits image data as multipart form data. Multer uses memory storage and checks allowed image types (JPG/JPEG, PNG, WebP) and file limits. The Cloudinary service sends the file buffer using `upload_stream`; it returns a secure URL and public ID, which are stored in the Vehicle image array or BusinessSettings logo fields. Vehicle upload accepts up to five images per upload, each at most 5 MB. Business settings accepts one logo image. Replacing a business logo attempts to remove the previous Cloudinary asset.

Cloudinary is configured only when all three Cloudinary credentials are present. Uploads fail with a user-facing/API error when the service is not configured or upload fails; no local persistent image storage is implemented.

## 16. Invoice data flow

An invoice can be created for an eligible booking after full payment. The invoice record stores a deterministic invoice number, booking/customer references, amount, issue date, and optional payment reference. The PDF download endpoint loads invoice-related booking, vehicle, customer, received payments, and BusinessSettings data, then creates an A4 PDFKit document and streams it to the client.

The business details used by the PDF include business name, address, city, state, pincode, phone, email, GSTIN, and logo where populated. The logo is optional and PDF generation tolerates an unavailable remote logo. The current controller streams the PDF; it does not upload generated PDFs to Cloudinary or populate `Invoice.pdfUrl`.

## 17. Business settings

Business Settings are restricted to Admin. The API reads or upserts a single record identified by the `main` singleton key. It stores the business identity/contact/address details and optional GSTIN/logo used for invoices. The application is single-business, not multi-tenant: no `shopId` or `tenantId` ownership model was found.

## 18. Authentication flow

Registration validates user details and creates a customer account; public input cannot assign a privileged role. Login checks credentials against the stored password hash, then returns a JWT access token and user data. The password field is excluded from ordinary queries and verified using `bcryptjs`. The client stores the access token in `localStorage`, keeps current user state in AuthContext, and sends the token as a Bearer header through Axios. Protected client routes redirect unauthenticated users and restrict role-specific pages. Backend middleware verifies tokens and loads the current user, then role and ownership checks gate operations.

The configured expiry is read from `JWT_EXPIRES_IN` (template default `1d`). No refresh-token flow was found. Users can update their own profile and change their password through `/users/me` endpoints; Admin separately manages staff accounts.

## 19. Error handling and validation

Controllers return JSON envelopes with `success`, `message`, and `data` or `errors` fields. The Express error handler maps Multer size/limit errors and unsupported image types to client errors and returns a generic 500 response for unexpected errors. Startup validates `JWT_SECRET`; database connection failures prevent a successful server start. Controllers validate IDs, required fields, dates, enum values, amounts, and operation state as appropriate; schemas provide field-level validation and unique indexes.

Authentication failures return unauthorized errors; insufficient role/ownership returns forbidden errors; missing records return not-found errors; duplicate-key conflicts are handled where uniqueness matters (for example invoice creation). MongoDB transaction failures are surfaced through controller error responses. No dedicated centralized validation library or exhaustive per-field API error catalog was found. Upload limits and supported formats are described in Section 15.

## 20. Security controls found in the code

- Passwords are hashed with `bcryptjs` (configured work factor 12 in the user model/controller path); plaintext passwords are not stored.
- JWT bearer tokens authenticate API requests; role authorization and ownership checks are applied on protected routes.
- Helmet sets HTTP security headers; CORS allows the configured `CLIENT_URL` origin (default local Vite origin).
- Login and registration each use a rate limiter with 20 requests per 15-minute window per client IP.
- JSON request bodies are limited to 20 KB. Image upload type/count/size are constrained.
- Secrets are read from backend environment variables. Keep MongoDB credentials, `JWT_SECRET`, and Cloudinary API secret out of source control and logs.
- Payment records store amount/method/reference and do not collect card numbers or process gateway credentials.

The frontend route guard improves navigation behavior but does not replace backend authorization. Production deployment should use HTTPS and production-grade environment secrets; deployment configuration itself is not included in the repository.

## 22. Deployment architecture

The repository does not include a hosting, Docker, or deployment manifest. A production deployment can use a static frontend host, a Node.js backend host, MongoDB Atlas, and Cloudinary:

```text
Browser → hosted React/Vite build → hosted Express API → MongoDB Atlas
                                            └──────────→ Cloudinary
```

Set the production frontend API URL with `VITE_API_URL` and configure the backend `CLIENT_URL` to match the deployed frontend origin. Backend credentials should be configured in the hosting provider's environment settings. Configure TLS/HTTPS at the hosting layer. The frontend must be rebuilt with its production API URL; backend and database must point to the intended production database.

## 24. How to run the project

Prerequisites: a supported Node.js/npm installation and a MongoDB instance reachable through `MONGODB_URI`. The repository README recommends Node.js 20.19+ or 22.12+; package manifests do not declare an `engines` field. Use a MongoDB replica set or Atlas for transaction-dependent booking, payment, pickup, and return operations.

1. Open two terminals in the project folder.
2. In the backend terminal:

   ```powershell
   cd server
   npm install
   Copy-Item .env.example .env
   ```

3. Edit `server/.env`: set `MONGODB_URI`, a strong `JWT_SECRET` (at least 32 characters and not a placeholder), `CLIENT_URL`, and the Cloudinary values if image uploads are needed. Set Admin seed values before creating the initial Admin.
4. Create the initial Admin once, then start the backend:

   ```powershell
   npm run seed:admin
   npm run dev
   ```

   The API defaults to port 5000. For a normal production start, use `npm start`.
5. In the frontend terminal:

   ```powershell
   cd client
   npm install
   npm run dev
   ```

6. Open the local address printed by Vite (normally `http://localhost:5173`). If the API is elsewhere, set `VITE_API_URL` for the client build/dev environment.

The health endpoint is `GET /api/v1/health`. The server connects to MongoDB before listening and refuses to start with a missing/weak JWT secret. Production startup also requires `CLIENT_URL`.

## 26. Admin setup

1. Configure a MongoDB URI and backend environment variables.
2. Set `ADMIN_NAME`, `ADMIN_EMAIL`, `ADMIN_PASSWORD`, and `ADMIN_MOBILE` in the backend environment.
3. Run `npm run seed:admin` from `server/`. It validates the seed values and refuses to create a second Admin when one already exists; it does not create an Admin through public signup.
4. Log in. Current Admin landing route is `/admin/dashboard`.
5. Use Staff Management to create Staff accounts. Public registration remains Customer-only.
6. Create categories, then vehicles; vehicle category references must point to existing categories.
7. Configure Business Settings for invoice identity/contact details.
8. Staff/Admin can then process booking requests, record payment receipts, perform pickups/returns, and manage maintenance.

## 27. Development workflow

Run `npm run dev` independently in `server/` and `client/`. The backend connects to the configured MongoDB instance; the Vite client uses `VITE_API_URL` or its local default. Cloudinary is needed for hosted image upload. Categories and vehicles are entered through Admin management screens; there is no vehicle seeding script. Changes to backend routes/controllers/models and frontend pages/components should be verified against their associated access rules and current API contract.

## 29. Testing and manual verification

No test directory or test script was found. The following is a manual checklist for implemented behavior:

- **Authentication:** public registration creates Customer; valid login succeeds; invalid credentials fail; role-protected pages/API reject unauthorized users.
- **Admin:** dashboard loads; staff can be created/listed/activated/deactivated; categories and vehicles can be managed; business settings save.
- **Staff:** booking list/review works; payments can be recorded; pickup/return forms create and complete rental records; maintenance can be scheduled and updated.
- **Customer:** browse vehicle list/detail; availability checks reflect dates; booking request appears pending; own booking, payments, invoices, and profile are scoped correctly.
- **Availability:** overlapping pending/approved booking is rejected; non-overlapping dates can be requested; unavailable vehicles cannot be booked.
- **Payment:** only eligible bookings accept a receipt; amount must equal remaining due; no gateway transaction is represented as processed.
- **Pickup/return:** pickup requires approved, due, available, fully paid booking; return odometer cannot be lower; damage return marks vehicle for maintenance.
- **Invoice:** eligible paid booking produces invoice; PDF downloads and includes available business details.
- **Notifications:** recipient can list and mark their notifications read; unread count updates in the client.
- **Cloudinary:** valid image uploads persist URL/public ID; unsupported type, oversized file, or missing configuration returns an error.
- **Reports:** staff/admin report API permissions and Admin-only revenue endpoint are respected.

## 30. Troubleshooting

| Symptom | Safe checks |
|---|---|
| MongoDB connection failure | Check `MONGODB_URI`, network/IP allow-list, database availability, and credentials. For transactional workflows use Atlas or a replica-set deployment. Never paste credentials into logs/issues. |
| CORS error | Set backend `CLIENT_URL` to the exact frontend origin, including scheme and port; restart backend after changing environment. |
| Wrong API URL | Check `VITE_API_URL`; it must include the API prefix, such as `/api/v1`. Rebuild/restart the frontend after changing it. |
| Cloudinary upload failure | Confirm all three Cloudinary environment variables, account availability, supported JPG/PNG/WebP type, and file-size/count limit. |
| JWT/authentication failure | Confirm `JWT_SECRET` is stable and at least 32 characters, token is present and unexpired, and the logged-in user remains active. Sign in again after changing secrets. |

## 31. Interview / resume architecture summary

Smart Car Rental is a single-business MERN-style application with a React/Vite SPA and an Express REST API backed by MongoDB/Mongoose. JWT authentication and server-side role/ownership middleware separate Admin, Staff, and Customer access. Booking creation checks overlapping pending/approved reservations inside a transaction, while lock-version updates help serialize concurrent booking and payment operations. Vehicle and business images are uploaded through Multer memory storage to Cloudinary. Staff/Admin record payment receipts rather than charging through a gateway. Pickup/return operations create a rental lifecycle with odometer and condition records, and damage can place a vehicle into maintenance. Invoice PDFs are generated by PDFKit from booking, customer, payment, and business settings data and streamed to the requester.
