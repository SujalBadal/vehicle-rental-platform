# Smart Car Rental API Routes

This reference lists routes mounted by the current Express application and verifies their behavior against the route modules, middleware, controllers, and relevant models. It describes implemented routes only.

## 1. Backend API overview

During local development, the default API base URL is:

```text
http://localhost:5000/api/v1
```

`server/src/server.js` uses `process.env.PORT || 5000`, and `server/src/app.js` mounts each API router below `/api/v1`. The frontend Axios client defaults to `http://localhost:5000/api/v1` and can be configured with `VITE_API_URL`. The API is served only after a successful MongoDB connection.

```text
React frontend
  → Axios API service (Bearer token when available)
  → Express app and mounted router (/api/v1)
  → authenticate / optionalAuthenticate
  → authorize role and controller ownership checks
  → controller
  → service and/or Mongoose model
  → MongoDB
```

Image uploads additionally pass through Multer memory storage and the Cloudinary service. PDF invoices are generated by the invoice controller with PDFKit and streamed to the response. The database is MongoDB via Mongoose; deployment may use MongoDB Atlas or another supported MongoDB deployment.

### Response conventions

JSON responses generally have this shape:

```json
{
  "success": true,
  "message": "...",
  "data": {}
}
```

Errors generally include `success: false`, a `message`, and `errors` (often an empty array; schema validation may return individual messages). A few endpoints return a binary PDF instead of JSON. Exact `data` members are noted for each operation below.

Unmatched API paths return HTTP 404 with `{ success: false, message: "API route not found.", errors: [] }`.

### Authentication terminology

- **Public:** no token required.
- **Optional bearer:** public when no Authorization header is present; a supplied bearer token is validated and can affect visible records or permissions.
- **Authenticated:** requires `Authorization: Bearer <JWT>` for an active account.
- **Admin / Staff:** authenticated account must have that role.
- **Owner or manager:** controller checks the associated customer, or allows Staff/Admin.

Authentication middleware reloads the account for each request and rejects missing, invalid, expired, or inactive accounts. `authorize(...)` returns 403 for a role mismatch. Authorization is applied server-side; a frontend route guard is not a substitute.

## 2. Authentication APIs

All three routes are mounted under `/api/v1/auth`. `POST /login` and `POST /register` are each rate-limited to 20 requests per 15 minutes per client IP.

### `POST /auth/register`

- **Authentication / role:** Public; creates a Customer account only.
- **Body:** `name`, `email`, `password`, `mobile`.
- **Validation:** All four are required; mobile is normalized by removing spaces/hyphens and must match a 10-digit Indian mobile number beginning 6–9; password must be at least 8 characters. Email is trimmed/lowercased for duplicate lookup and schema validation. Duplicate email returns 409.
- **Security behavior:** Controller explicitly writes `role: "customer"`; a submitted `role` field is not used. Public registration cannot create Staff/Admin accounts.
- **Success:** HTTP 201, `{ success, message, data: { token, user } }`; password is removed from the returned user.
- **Common errors:** 400 required/format/schema validation, 409 duplicate email, 500 account creation failure, rate limit response.

### `POST /auth/login`

- **Authentication / role:** Public.
- **Body:** `email`, `password`.
- **Validation / behavior:** Both required. Email is trimmed/lowercased; password is compared with the stored bcrypt hash. Inactive accounts are rejected.
- **Success:** HTTP 200, `{ success, message, data: { token, user } }`; user excludes password.
- **Common errors:** 400 missing fields, 401 bad credentials or inactive account (same credential message), 500 login failure, rate limit response.

### `GET /auth/me`

- **Authentication / role:** Authenticated; any active role.
- **Parameters/body:** None.
- **Success:** HTTP 200, `{ success, message, data: { user } }`, with password excluded.
- **Common errors:** 401 invalid/unavailable account or token, 500 load failure.

## 3. Staff and managed-user APIs

There is no standalone `/staff` router. Staff management is implemented by Admin-only endpoints under `/api/v1/users`. Only Staff accounts can be listed, updated, or have status changed through these management routes. There is no staff detail-by-ID or delete endpoint.

### `GET /users?role=staff`

- **Permission:** Admin only.
- **Query:** `role` is required and must equal `staff`; other values return 400.
- **Success:** HTTP 200, `{ data: { users } }`. Returned fields are limited to `name`, `email`, `mobile`, `role`, `isActive`, and `createdAt`, sorted by name.
- **Errors:** 400 role query invalid; 401/403 auth; 500 database failure.

### `POST /users/staff`

- **Permission:** Admin only.
- **Body:** `name`, `email`, `password`, `mobile`.
- **Validation / behavior:** All required; normalized Indian mobile format; password at least 8 characters; email lowercased; duplicate email returns 409. Server sets role to `staff`; caller cannot choose another role. Password is bcrypt-hashed.
- **Success:** HTTP 201, `{ data: { user } }`; password excluded.
- **Errors:** 400 missing/invalid values or model validation; 409 duplicate email; 401/403 auth; 500 create failure.

### `PATCH /users/:id`

- **Permission:** Admin only; target must be a Staff account.
- **Path:** `id` must be a valid user MongoDB ID.
- **Body:** `name`, `mobile` (both required by the controller for this update).
- **Success:** HTTP 200, `{ data: { user } }`; password excluded.
- **Errors:** 400 invalid ID or name/mobile validation, 404 Staff account not found, 401/403 auth, 500 update failure.

### `PATCH /users/:id/status`

- **Permission:** Admin only; target must be another Staff account.
- **Body:** `isActive` must be a boolean.
- **Behavior:** Prevents the Admin from deactivating their own account through this endpoint. A missing, non-Staff, or self target returns 404.
- **Success:** HTTP 200, `{ data: { user } }`; password excluded.
- **Errors:** 400 invalid ID or status value, 404 Staff account not found, 401/403 auth, 500 update failure.

**Not implemented:** staff deletion, `GET /users/:id`, and a separate Staff router.

## 4. Vehicle APIs

Mounted under `/api/v1/vehicles`.

### `GET /vehicles`

- **Permission:** Public with optional bearer authentication. `includeUnavailable=true` requires an authenticated Staff/Admin user.
- **Query:** `search` (make/model substring, escaped and case-insensitive), `category` (category ID), `transmission`, `fuelType`, `seats` (positive integer; returns vehicles with at least that many seats), `minPrice`, `maxPrice` (non-negative numbers), `sort` (`price_asc`, `price_desc`, `newest`, `year_desc`), `page`, `limit` (1–50; defaults page 1, limit 12), `includeUnavailable=true` (Staff/Admin only).
- **Behavior:** By default only `available` vehicles are returned. Populates category name.
- **Success:** HTTP 200, `{ data: { vehicles, pagination: { page, limit, total, pages } } }`.
- **Errors:** 400 invalid category/seats/price filters; 403 unauthorized unavailable-vehicle request; 401 if an invalid supplied bearer token; 500 list failure.

### `GET /vehicles/:id/availability?pickupDate=YYYY-MM-DD&returnDate=YYYY-MM-DD`

- **Permission:** Public; this route does not use authentication middleware.
- **Path/query:** Vehicle `id`; both dates required and valid, with return later than pickup.
- **Behavior:** Available only when vehicle status is `available` and no `pending` or `approved` booking overlaps (`existing pickup < requested return` and `existing return > requested pickup`).
- **Success:** HTTP 200, `{ data: { vehicleId, pickupDate, returnDate, available, reason } }`.
- **Errors:** 400 invalid dates/ID, 404 vehicle missing, 500 availability check failure.

### `GET /vehicles/:id`

- **Permission:** Public with optional bearer authentication. Available vehicles are visible publicly; authenticated Staff/Admin may view unavailable vehicles too.
- **Success:** HTTP 200, `{ data: { vehicle } }`, with category name and description populated.
- **Errors:** 400 malformed ID, 401 invalid supplied token, 404 not found/not publicly visible, 500 load failure.

### `POST /vehicles`

- **Permission:** Staff/Admin.
- **Body:** `category`, `make`, `model`, `year`, `registrationNumber`, `description`, `transmission`, `fuelType`, `seats`, `pricePerDay`, optional `status` (defaults to `available`). Images are managed separately.
- **Validation:** Category must exist and be active. Schema constrains required values, year 1900–2100, transmission `manual|automatic`, fuel type `petrol|diesel|hybrid|electric|other`, seats 1–50, price non-negative, and unique registration number.
- **Success:** HTTP 201, `{ data: { vehicle } }`.
- **Errors:** 400 category/details, 409 duplicate registration, 401/403 auth, 500 create failure.

### `PUT /vehicles/:id`

- **Permission:** Staff/Admin.
- **Body:** Any subset of `category`, `make`, `model`, `year`, `registrationNumber`, `description`, `transmission`, `fuelType`, `seats`, `pricePerDay`, `status`; only these fields are copied from the request. Changed category must be active. Schema validators run.
- **Success:** HTTP 200, `{ data: { vehicle } }`, with category name populated.
- **Errors:** 400 invalid ID/category/schema, 404 missing vehicle, 409 duplicate registration, 401/403 auth, 500 update failure.

### `PATCH /vehicles/:id/status`

- **Permission:** Staff/Admin.
- **Body:** `status` must be `available`, `rented`, `maintenance`, or `inactive`.
- **Success:** HTTP 200, `{ data: { vehicle } }`.
- **Errors:** 400 invalid status/ID, 404 missing vehicle, 401/403 auth, 500 update failure.

### `DELETE /vehicles/:id`

- **Permission:** Admin only.
- **Behavior:** Vehicle cannot be deleted if any booking or maintenance record references it; API advises setting status to inactive instead.
- **Success:** HTTP 200, `{ data: {} }`.
- **Errors:** 400 invalid ID, 404 missing vehicle, 409 vehicle has booking/maintenance history, 401/403 auth, 500 delete failure.

### `POST /vehicles/:id/images`

- **Permission:** Staff/Admin.
- **Content type/body:** `multipart/form-data`, repeat file field `images`; optional query `replace=true` replaces current images, otherwise uploads append.
- **Upload behavior:** Multer memory storage, JPG/JPEG (`image/jpeg`), PNG, WebP; max five files per request and 5 MiB per file; max five images stored per vehicle. The controller sends each buffer through Cloudinary `upload_stream` in `smart-car-rental/vehicles`; MongoDB stores returned `url` and `publicId`. Replaced old Cloudinary files are deleted on a best-effort basis after saving the new references.
- **Success:** HTTP 201, `{ data: { vehicle, images, cleanupFailed } }`.
- **Errors:** 400 invalid ID/no files/vehicle image limit/type, 401/403 auth, 404 vehicle missing, 413 file too large, 503 Cloudinary not configured, 502 upload failure.

### `DELETE /vehicles/:id/images`

- **Permission:** Staff/Admin.
- **Body:** `publicId` identifying an image on that vehicle.
- **Behavior:** Removes matching Cloudinary image and removes it from the Vehicle images list.
- **Success:** HTTP 200, `{ data: { images } }`.
- **Errors:** 400 invalid vehicle ID, 401/403 auth, 404 vehicle/image missing, 503 Cloudinary not configured, 502 removal failure.

## 6. Booking APIs

Mounted under `/api/v1/bookings`; `router.use(authenticate)` protects every route.

### `GET /bookings`

- **Permission:** Any authenticated role. Customers are scoped to their own bookings; Staff/Admin see all. Optional `status` query filters by exact status.
- **Success:** HTTP 200, `{ data: { bookings } }`; vehicle, customer, and reviewer names/details are populated; newest first.
- **Errors:** 401 auth, 500 list failure.

### `POST /bookings`

- **Permission:** Customer only.
- **Body:** `vehicleId`, `pickupDate`, `returnDate`, optional `pickupLocation`.
- **Validation / behavior:** Dates must be valid `YYYY-MM-DD`; return after pickup; pickup not in past (UTC day); vehicle ID valid and vehicle available. Rejects overlap with pending/approved bookings. In a transaction, increments a vehicle lock version, checks overlap, calculates rental days with `ceil(duration in days)`, copies current `pricePerDay` to `dailyRate`, computes `totalPrice`, and creates status `pending`. Sends in-app notifications after successful creation.
- **Success:** HTTP 201, `{ data: { booking } }` with vehicle/customer populated.
- **Errors:** 400 invalid fields/date/ID, 401 auth, 403 wrong role, 404 vehicle missing, 409 unavailable/overlap, 503 if MongoDB transactions are unsupported, 500 other failure.

### `GET /bookings/:id`

- **Permission:** Owner customer or Staff/Admin.
- **Success:** HTTP 200, `{ data: { booking } }`; vehicle, customer, and reviewer populated.
- **Errors:** 400 invalid ID, 401 auth, 403 not owner/manager, 404 missing booking, 500 load failure.

### `PATCH /bookings/:id/cancel`

- **Permission:** Owner customer or Staff/Admin.
- **Body:** Not used.
- **Behavior:** Only `pending` or `approved` bookings with future pickup dates can be cancelled. Sets status to `cancelled` and sends notifications.
- **Success:** HTTP 200, `{ data: { booking } }`.
- **Errors:** 400 invalid ID, 401 auth, 403 not owner/manager, 404 missing booking, 409 status/date not cancellable, 500 failure.

### `PATCH /bookings/:id/decision`

- **Permission:** Staff/Admin (role middleware).
- **Body:** `status` must be `approved` or `rejected`; optional `rejectionReason` is used for a rejection.
- **Behavior:** Only a `pending` booking may be decided. Stores reviewer and review time, and rejection reason when rejected. Notifies the customer.
- **Success:** HTTP 200, `{ data: { booking } }`.
- **Errors:** 400 invalid decision/ID, 401/403 auth, 404 missing booking, 409 booking not pending, 500 update failure.

Booking model status values: `pending`, `approved`, `rejected`, `cancelled`, `completed`. There is no separate general booking status endpoint; decisions and cancellation use the routes above, and a successful rental return changes an approved booking to completed.

## 7. Payment APIs

Mounted under `/api/v1/payments`; all routes require authentication.

### `GET /payments?bookingId=<id>`

- **Permission:** Authenticated. Customer results are restricted to their own payments; Staff/Admin can list all. Optional `bookingId` filters results and must be a valid MongoDB ID.
- **Success:** HTTP 200, `{ data: { payments } }`; populated booking/vehicle, customer, and recording user; newest receipt first.
- **Errors:** 400 invalid booking ID, 401 auth, 500 list failure.

### `POST /payments`

- **Permission:** Staff/Admin.
- **Body:** `bookingId`, `amount`, `method` (`cash`, `upi`, `card`), optional `transactionReference` (required for UPI/card).
- **Validation / behavior:** Amount must be positive and exactly equal the outstanding balance. Booking must be `approved` or `completed`. Received payments are summed inside a MongoDB transaction; a lock version serializes concurrent attempts. Creates status `received`, assigns current user as `recordedBy`, and notifies customer. It records a payment receipt; no online transaction is processed.
- **Success:** HTTP 201, `{ data: { payment } }` with booking/vehicle, customer, and recorder populated.
- **Errors:** 400 bad booking ID/amount/method/reference/model validation; 401/403 auth; 404 booking missing; 409 ineligible booking, already paid, or incorrect outstanding amount; 503 transaction support unavailable; 500 failure.

Payment methods in the model are `cash`, `upi`, and `card`; statuses are `received` and `refunded`. No payment detail, refund, or status-update endpoint is registered. The implementation records a transaction reference for UPI/card but does not accept/store card number, CVV, or UPI PIN fields and does not connect to a payment gateway.

## 8. Rental, pickup, and return APIs

All routes under `/api/v1/rentals` require Staff/Admin. There is no rental detail-by-ID endpoint.

### `GET /rentals?status=<active|completed>`

- **Permission:** Staff/Admin.
- **Query:** Optional status filter is passed to the query; model statuses are `active` and `completed`.
- **Success:** HTTP 200, `{ data: { rentals } }`; booking, vehicle, and customer populated; newest first.
- **Errors:** 401/403 auth, 500 list failure.

### `POST /rentals/bookings/:bookingId/pickup`

- **Permission:** Staff/Admin.
- **Body:** `pickupOdometer` (non-negative finite number), optional `pickupConditionNotes`.
- **Behavior:** Booking must exist, be approved, and pickup date must have arrived. Full booking price must be recorded as received; vehicle must be available. A transaction marks vehicle rented and creates one active Rental for the booking. A duplicate rental is rejected by unique booking constraint. No fuel field is implemented.
- **Success:** HTTP 201, `{ data: { rental } }`; booking, vehicle, customer populated.
- **Errors:** 400 invalid ID/odometer, 401/403 auth, 404 booking missing, 409 booking/date/payment/vehicle conflict or duplicate rental, 503 transaction support unavailable, 500 failure.

### `PATCH /rentals/:id/return`

- **Permission:** Staff/Admin.
- **Body:** `returnOdometer` (finite, non-negative, and at least pickup reading), optional `returnConditionNotes`, `damageReported` boolean or string `"true"`, optional `damageNotes`.
- **Behavior:** Requires active rental; transaction records return, completes rental, changes associated approved booking to completed, and sets vehicle to `available` or `maintenance` when damage is reported. A second return will not find an active rental.
- **Success:** HTTP 200, `{ data: { rental } }`; message indicates if referred for maintenance.
- **Errors:** 400 invalid ID/odometer, 401/403 auth, 404 no active rental, 409 inconsistent vehicle status, 503 transaction support unavailable, 500 failure.

Rental statuses: `active`, `completed`. Implemented handover fields include pickup/return odometer and condition notes, damage flag and notes; fuel readings are not implemented.

## 9. Maintenance APIs

All routes under `/api/v1/maintenance` require Staff/Admin.

### `GET /maintenance?status=<status>&vehicleId=<id>`

- **Query:** Optional `status` and `vehicleId`; ID is validated. Records are populated with vehicle and creator/performer and sorted by scheduled date descending.
- **Success:** HTTP 200, `{ data: { maintenance: [...] } }`.
- **Errors:** 400 invalid vehicle ID, 401/403 auth, 500 list failure.

### `POST /maintenance`

- **Body:** `vehicleId`, `serviceType`, `description`, `scheduledAt`, optional `cost` (defaults to 0), optional `notes`.
- **Validation / behavior:** Valid vehicle ID, nonblank service type/description, valid date, non-negative cost. Vehicle must exist and have `available` or `maintenance` status. Transaction creates `scheduled` record and marks vehicle `maintenance`; active Admins are notified.
- **Success:** HTTP 201, `{ data: { maintenance } }`.
- **Errors:** 400 invalid input, 401/403 auth, 404 vehicle missing, 409 vehicle state disallows scheduling, 503 transaction support unavailable, 500 failure.

### `PUT /maintenance/:id`

- **Body:** Optional subset of `description`, `serviceType`, `scheduledAt`, `cost`, `notes`; Mongoose validators run.
- **Success:** HTTP 200, `{ data: { maintenance } }` with vehicle populated.
- **Errors:** 400 invalid ID/schema, 401/403 auth, 404 record missing, 500 failure.

### `PATCH /maintenance/:id/start`

- **Body:** Not used.
- **Behavior:** Only a `scheduled` record can transition to `in_progress`.
- **Success:** HTTP 200, `{ data: { maintenance } }`.
- **Errors:** 400 invalid ID, 401/403 auth, 409 missing record or not scheduled, 500 failure.

### `PATCH /maintenance/:id/complete`

- **Body:** Optional `cost` override.
- **Behavior:** Only `scheduled` or `in_progress` records are open. Sets `completed`, completion time, current user as performer, and optional cost. If no other open maintenance exists for the vehicle, restores it to available only if its vehicle status is still `maintenance`.
- **Success:** HTTP 200, `{ data: { maintenance } }`.
- **Errors:** 400 invalid ID/model data, 401/403 auth, 404 no open record, 503 transaction support unavailable, 500 failure.

### `PATCH /maintenance/:id/cancel`

- **Body:** Not used.
- **Behavior:** Cancels a scheduled/in-progress record; if no other open maintenance remains, the same conditional vehicle-status restoration applies.
- **Success/errors:** Same response envelope and broad error classes as completion.

Maintenance statuses: `scheduled`, `in_progress`, `completed`, `cancelled`.

## 10. Business Settings APIs

Both routes under `/api/v1/business-settings` have router-level authentication and Admin authorization.

### `GET /business-settings`

- **Permission:** Admin only.
- **Success:** `{ data: { settings } }`; settings may be `null` before initial save.
- **Errors:** 401/403 auth, 500 load failure.

### `PUT /business-settings`

- **Permission:** Admin only.
- **Body:** JSON fields `businessName`, `phone`, `email`, `address`, `city`, `state`, `pincode`, `gstin`; optional logo as multipart file field `logo`. When sending a file, send the text fields as multipart fields too.
- **Validation:** `businessName`, `phone`, `address`, and `city` are required; supplied email must match a basic email format. Model length/required rules also apply.
- **Image handling:** Multer single-file memory buffer, JPG/PNG/WebP and 5 MiB; Cloudinary upload to `smart-car-rental/business`. Replaces/deletes an old logo best-effort. Omit logo to retain the existing logo.
- **Success:** `{ data: { settings } }`, upserted singleton record (`singletonKey: main`).
- **Errors:** 400 missing/invalid values or file type; 401/403 auth; 413 too large; 503 Cloudinary unavailable when logo submitted; 500 save failure.

The same singleton settings record is loaded by invoice PDF generation for business identity/contact/logo. There is no public read endpoint.

## 11. Invoice APIs

All invoice endpoints require authentication. Customer records are scoped to their own account; Staff/Admin are allowed to access any customer's invoice by controller checks. No invoice update/delete endpoint exists.

### `GET /invoices`

- **Permission:** Authenticated; customer sees own invoices, Staff/Admin see all.
- **Success:** HTTP 200, `{ data: { invoices } }`; booking dates/total/status and customer name/email populated, sorted newest issued first.
- **Errors:** 401 auth, 500 list failure.

### `POST /invoices/bookings/:bookingId`

- **Permission:** Authenticated booking owner or Staff/Admin.
- **Behavior:** Booking must be `approved` or `completed` and fully paid according to received payment records. Creates one invoice per booking with number `INV-` plus uppercase booking ObjectId. If already present, returns the existing invoice (the route still uses HTTP 201). Customer is notified only when newly created.
- **Success:** HTTP 201, `{ data: { invoice } }`.
- **Errors:** 400 invalid booking ID, 401 auth, 403 not owner/manager, 404 booking missing, 409 status/payment ineligible, 500 failure.

### `GET /invoices/:id`

- **Permission:** Invoice's customer or Staff/Admin.
- **Success:** HTTP 200, `{ data: { invoice } }`; booking, vehicle, and customer populated.
- **Errors:** 400 invalid invoice ID, 401 auth, 403 not owner/manager, 404 invoice missing, 500 failure.

### `GET /invoices/:id/pdf`

- **Permission:** Same owner/Staff/Admin check as invoice detail.
- **Success:** `application/pdf`, attachment filename `<invoiceNumber>.pdf`; generated with PDFKit on A4 and streamed. Includes booking/customer/vehicle, recorded payments, and configured business details where present. Logo fetch is limited to HTTPS `res.cloudinary.com` and times out after five seconds; a missing/unavailable logo does not prevent the PDF.
- **Errors:** 400 invalid ID, 401 auth, 403 not owner/manager, 404 invoice missing, 500 JSON error if headers have not been sent (stream may be destroyed for a later failure).

`Invoice.pdfUrl` exists in the model but the current controller does not persist the generated PDF there.

- **Errors:** 401 auth, 500 load failure.

### `PATCH /notifications/read-all`

- **Body:** Not used.
- **Behavior:** Marks all current user's unread notifications as read.
- **Success:** HTTP 200, `{ data: {} }`.
- **Errors:** 401 auth, 500 update failure.

### `PATCH /notifications/:id/read`

- **Body:** Not used.
- **Behavior:** Sets `readAt` only for a notification owned by current user.
- **Success:** HTTP 200, `{ data: { notification } }`.
- **Errors:** 400 invalid ID, 401 auth, 404 not found or not owned, 500 update failure.

Notifications are in-app database records created by application workflows; no email notification route is registered.

## 13. User and profile APIs

Mounted under `/api/v1/users`; `router.use(authenticate)` applies to all endpoints. See Section 3 for the Admin staff-management operations.

### `GET /users/me`

- **Permission:** Any authenticated role; current user only.
- **Success:** HTTP 200, `{ data: { user } }`, password omitted.
- **Errors:** 401 auth, 404 account missing, 500 is not explicitly caught in this handler (an unexpected error reaches Express error handler).

### `PATCH /users/me`

- **Permission:** Any authenticated role; cannot change role/email/status through this endpoint.
- **Body:** `name`, `mobile` (both required); mobile allows spaces/hyphens before normalization and must become a valid 10-digit Indian number.
- **Success:** HTTP 200, `{ data: { user } }`, password omitted.
- **Errors:** 400 invalid details, 401 auth, 404 account missing; unexpected database errors are not explicitly caught here.

### `PATCH /users/me/password`

- **Permission:** Any authenticated role; current account only.
- **Body:** `currentPassword`, `newPassword`.
- **Validation:** Both required; new password at least 8 characters; current password must verify. New password hashed with bcrypt.
- **Success:** HTTP 200, `{ success, message }` (no user data).
- **Errors:** 400 missing values/short new password/incorrect current password, 401 auth, 404 account missing; unexpected errors are not explicitly caught in this handler.

There is no general user listing, customer management, customer account status API, account deletion API, or standalone account-status read endpoint. `GET /users?role=staff` and Admin staff management endpoints are described in Section 3.

## 14. Health and system APIs

### `GET /health` → `/api/v1/health`

- **Permission:** Public.
- **Behavior:** Checks `mongoose.connection.readyState`.
- **Success:** HTTP 200 when connected, `{ success: true, message: "API and database are ready.", data: { api: "ok", database: "connected" } }`.
- **Failure:** HTTP 503 when disconnected with `success: false` and database `disconnected`.

No other test, upload-test, or system endpoint was registered. Authentication endpoints have their own rate-limit middleware; no separate rate-limit status endpoint exists.
